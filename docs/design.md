# mc-deploy — стандартний автодеплой модів на сервери (дизайн)

**Дата:** 2026-08-15 · **Статус:** погоджено з власником, чекає імплементації
**Мета:** будь-який мод-реп орги підключається до автодеплою на Pterodactyl-сервер
одним файлом; уся логіка і майже всі секрети — в одному центральному репі.

## Контекст і рішення, ухвалені під час обговорення

- Усі цільові сервери живуть на **одній Pterodactyl-панелі**.
- Репи модів **приватні**, в орзі `borukva` на **free-плані** (плюс кілька в
  `DagerPMC`). Org-секрети для приватних реп на free-плані **не працюють**
  (перевірено) — тому секрети роздаються авторозсилкою (див. нижче).
- Деплой запускається **автоматично одразу після публікації релізу**, без
  approve-гейтів. Тег/реліз і так ставиться свідомо — це і є момент рішення
  «шипимо».
- Спільний знаменник усіх реп — **подія «GitHub Release опубліковано»**, а не
  спосіб його створення: у одних репах реліз робить softprops-екшен на тег
  `v*` (mindbattle, borukva-party), в інших — `./gradlew githubRelease` на тег
  `*` (bridge, map-tools). Деплой чіпляється до готового релізу і **викачує
  джар з його асетів** — деплоїться байт-у-байт те, що в релізі, без
  перезбирання.
- Розглядався і відхилений варіант централізованого reconciler-а (деплой
  виконується в mc-deploy по крону, в модах лише `.deploy.json`, секрети ніде
  не розсилаються): власник обрав event-driven модель із секретами на рівні
  реп — деплой миттєвий, без cron-затримки.

## Архітектура

Новий **публічний** реп `borukva/mc-deploy`:

```
mc-deploy/
├── deploy.py                          # уся логіка деплою (Python, stdlib-only)
├── servers.json                       # реєстр серверів: аліас → Ptero server id
├── .github/workflows/
│   ├── deploy.yml                     # reusable workflow (on: workflow_call)
│   └── sync-secrets.yml               # авторозсилка секретів по репах орги
└── README.md                          # онбординг репу за 2 кроки
```

Публічність обов'язкова: публічні reusable workflows можна викликати з
будь-якого репу будь-якого власника (закриває і `borukva`, і `DagerPMC`).
Секретів у самому репі немає — тільки в його Actions-секретах.

### Підключення мод-репу = один файл

`.github/workflows/deploy.yml` у репі мода (~15 рядків):

```yaml
name: Deploy
on:
  release:
    types: [published]
  workflow_dispatch:           # ручний редеплой/відкат на будь-який тег
    inputs:
      tag: {description: "Тег релізу (порожньо = останній)", required: false}

jobs:
  deploy:
    uses: borukva/mc-deploy/.github/workflows/deploy.yml@v1
    with:
      targets: |
        mindbattle-pvp-*.jar -> mindbattle-pvp
        mindbattle-*.jar     -> mindbattle-main
      tag: ${{ inputs.tag || github.event.release.tag_name }}
    secrets:
      PTERO_URL: ${{ secrets.PTERO_URL }}
      PTERO_TOKEN: ${{ secrets.PTERO_TOKEN }}
```

### `targets` — мапінг «глоб асета → аліас сервера»

- Один рядок = «асети за цим глобом їдуть на цей сервер». Покриває
  1 джар → 1 сервер, 2 джари → 2 сервери (mindbattle), 1 джар → N серверів
  (N рядків з одним глобом).
- **Роутинг-правило:** рядки обробляються по черзі, кожен асет забирає
  перший глоб, який його зматчив. Тому специфічніший глоб
  (`mindbattle-pvp-*`) пишеться вище загального (`mindbattle-*`).
- Аліаси резолвляться через `servers.json` у mc-deploy — Ptero-айді не
  розкидані по репах. Правити `servers.json` треба лише коли з'являється
  **новий сервер** (рідкісна подія); новий мод на відомий сервер нічого в
  mc-deploy не змінює.
- Короткі Ptero-айді в публічному `servers.json` — свідомий компроміс: без
  URL панелі й токена (обидва — секрети) айді інертний.

## Семантика deploy.py (узагальнений `abyss/tools/remote.py push-mod`)

Для кожного target послідовно (порядок = порядок рядків; кілька таргетів
одного репу деплояться в одному джобі, тож правило mindbattle «обидва сервери
на одній версії» виконується автоматично):

1. Викачати з релізу асет за глобом. 0 або >1 збіг → падіння з поясненням.
2. `GET files/list mods/` → знайти застарілі джари цього мода. Префікс мода
   виводиться з глоба (усе до першого `*`), з тим самим роутинг-правилом,
   щоб `mindbattle-` не зачепив `mindbattle-pvp-*.jar`.
3. Аплоад нового джара (ім'я з версією → колізій немає), потім видалення
   застарілих. Видалення відкритого файлу на Linux безпечне — так само
   працює `push-mod` сьогодні.
4. `POST power restart`.
5. Полінг консольного лога до boot-ok маркера (дефолт `Done (`,
   перевизначається інпутом `boot_ok` — напр. `Abyss initialized`); падіння
   на boot-bad маркерах (`Mixin apply ... failed`, краш). Таймаут ~3 хв.
6. Немає чистого буту → джоба червона. Автовідкату немає (свідомо: рестарт
   назад — теж рестарт по живих гравцях); відкат — руками, див. нижче.

Захисти в reusable workflow:

- `concurrency` серіалізує деплої одного репу (GitHub-групи — per-repo, тож
  два РІЗНІ репи на один сервер вони не серіалізують); на цей рідкісний
  випадок deploy.py перед діями чекає, поки сервер вийде зі стану
  `starting`/`stopping`.
- Логи джоби мінімальні й несенситивні (панельний URL — секрет, GitHub його
  маскує сам).

## Секрети

**Канонічне сховище — Actions-секрети самого mc-deploy** (єдине місце, яке
заводиться руками):

- `PTERO_URL` — адреса панелі;
- `PTERO_TOKEN` — client API токен (`ptlc_…`, той самий, що в `remote.py`);
- `REPO_ADMIN_TOKEN` — fine-grained PAT з правом `secrets: write` на репи
  орги (за потреби — другий на `DagerPMC`, PAT прив'язаний до одного
  власника).

**Роздача — `sync-secrets.yml` у mc-deploy**, без жодної локальної машини:

- Тригери: cron раз на день + `workflow_dispatch` (кнопка).
- Логіка: лістить усі репи орг(и) → у кого існує
  `.github/workflows/deploy.yml`, тому ставить/оновлює `PTERO_URL` і
  `PTERO_TOKEN` через `REPO_ADMIN_TOKEN`.
- **Реєстру реп немає**: наявність `deploy.yml` у репі і є фактом
  «підключений». Новий мод = комміт одного файлу в самому моді; секрети
  приїдуть кроном або однією кнопкою.
- Ротація токена панелі: оновити секрет у mc-deploy → Run workflow → усі
  репи оновлені.
- Якщо орга колись перейде на платний Team-план — sync-secrets просто
  відмирає на користь двох org-секретів; воркфлоу модів не змінюються
  (вони читають `secrets.PTERO_URL`/`PTERO_TOKEN`, звідки ті взялися —
  байдуже).

## Редеплой і відкат

Старі релізи зберігають джари, тож відкат = деплой старого релізу:
у репі мода → Actions → Deploy → Run workflow → вписати попередній тег.
Той самий шлях — редеплой поточної версії після ручних маніпуляцій на
сервері.

## Версіонування mc-deploy

Мод-репи посилаються на `@v1` (мажорний тег, як у сторонніх екшенів).
Фікси = пересунути `v1`; ламальна зміна контракту (`targets`, інпути,
секрети) = `v2`, репи мігрують кожен у своєму темпі.

## Онбординг репу (вміст README у mc-deploy)

1. Скопіювати шаблонний `deploy.yml`, вписати свої `targets`.
2. Якщо сервера ще немає в `servers.json` — додати рядок (єдиний випадок,
   коли чіпається mc-deploy).
3. Якщо реп ще не робить релізів (abyss, lobby, minigames) — скопіювати
   стандартний `release.yml` з mindbattle (тег `v*` → збірка → реліз із
   джаром).

## Свідомо поза скоупом

- **Кімнати, моделі, конфіги abyss** — і далі `remote.py`
  (`push-rooms`/`push-models`): там прод — source of truth, автодеплой із
  git був би небезпечний. mc-deploy деплоїть **тільки джари**.
- `remote.py push-mod` лишається як ручний шлях для дев-ітерацій без релізу.
- Approve-гейти: не потрібні зараз; за бажанням будь-який реп може сам
  повісити environment protection на свою deploy-джобу, контракт від цього
  не зміниться.

## Критерії успіху

1. Тег у mindbattle → реліз → обидва сервери (main + pvp) самі отримали нові
   джари, рестартнули і чисто забутились; джоба зелена.
2. Підключення наступного репу зайняло: 1 файл у репі + (якщо новий сервер)
   1 рядок у `servers.json`.
3. Відкат на попередній тег через Run workflow працює.
4. Зіпсований джар (сервер не бутиться) → червона джоба, зрозуміле
   повідомлення; сервер лишається як є до ручного втручання.
